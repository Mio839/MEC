## 2. Phase 1 — セレモニーの交通整理【不具合修正を含む・最初にやる】

### 2-1. `ceremony()` にキューが無い（実害のあるバグ）

`gamify.js` の `ceremony(html, opts)`：

```js
ov.innerHTML = '<div class="gm-cer">' + html + '</div>';
ov.classList.add('show');
```

**上書きするだけでキューが無い。** 近接して2つ発火すると、先に描いた方は誰にも見られないまま消える。

しかもこれが起きる条件が「40問目」そのもの：

```
onAnswer()
  └ _bumpMission()  → _checkMissionCompletions() → ceremony('MISSION COMPLETE')
  └ _afterEvent()   → _checkLevelUp(true)        → ceremony('LEVEL UP')   ← 上書き
```

**同じ同期呼び出しの中で連続する。** 日次ミッション達成とレベルアップが重なる解答では、
MISSION COMPLETE は一瞬描かれて即座に消える。

`ceremony()` を呼ぶのは4か所（レベルアップ／章制覇／科目制覇／ミッション全達成）。
**`toast()` は既に `_toastQ` + `_drainToast()` でキューを持っている**ので、同じ作りにする。

### 2-2. `_afterEvent` が `examMode` を見ていない

```js
function _afterEvent(uid) {
  _statsCache = null;
  _updateHeaderChips();
  _checkLevelUp(true);        // ← 試験中でも全画面セレモニー(2.4秒)が出る
  _checkAchievements(true);
  if (uid) { _checkChapterClear(uid); _checkSubjectClear(uid); }
  _rerenderHubPanel();
}
```

`_microLapFx` と `_lapMilestoneFx` は先頭で `if (examMode) return;` しているのに、
**一番大きい全画面セレモニーだけが素通し**。試験の tier 演出の真上に被る。

### 2-3. 実装方針

1. `ceremony()` をキュー化する（`toast()` と同型。順に再生し、前のものが消えてから次を出す）。
2. **試験中に発生したセレモニーは溜めておき、結果画面（`showExamSummary`）で順に再生する。**
   - tier 演出との衝突が消える。
   - 結果画面が「この1本で何を達成したか」の場になる＝**外した自己ベスト・前回比の穴がここで埋まる**。
   - データ追加ゼロ。
3. 実績（`_checkAchievements`）は `toast()` 経由でキュー済みなので、そのままでよい。
   ただし**試験中はトーストも溜める**かは実装時に判断する（トーストは小さいので出しても害は小さい）。

⚠️ **`gamify.js` は study.html でも読み込まれている**（`<script src="gamify.js">` が script 一覧にある）。
ハブ専用ではないので、study.html 側で発火することを前提に組むこと。

⚠️ レベルアップが「上がったその場」ではなく結果画面で出ることになる。
**これはユーザーが承諾済みの仕様変更**（集中を切らないことを優先）。

### 2-4. テスト

`_work/test_gamify_ceremony.js`（新規）。既存テストと同じく**実ソースを読み込む**方式で書く。

- キューに2つ積んだとき、1つ目が最後まで再生されてから2つ目が出ること
- `examMode` が真の間は再生されず、解除後（結果画面）にまとめて再生されること
- 溜まったものが失われないこと（順序も保つ）

## 3. Phase 2 — 試験経路の演出【本命】

### B1. 科目読み込みの待ちが完全に無演出【最優先】

`study.html` の `toggleSubjectChip()`：

```js
const need = [...selectedSubjects].filter(s => !_loadedSids.has(s));
if (need.length) Promise.all(need.map(s => _fetchSubjectCards(s))).then(_finish);
else _finish();
```

**最大594問（神経）のJSONを fetch する間、表示が一切ない。**
押した手応えも `_syncChipStyles()` の色替えだけ。

**経路の中で唯一の無演出区間であり、毎回必ず通り、毎回いちばん長く待つ場所。**

- チップ自体が「読み込み中」を持つ（縁の脈・進捗リング）。
  ハブの `.cta-redo[data-load]::before` と同じ作りが流用できる。
- カードは上から波状に着地させる（`--i` スタッガー。ハブのボタン入場 E3 と同じ手法）。
- 完了時に科目色で一度だけ走査（`MecFX.wave`＝既存エミッタ。新規追加は不要）。

⚠️ `_unloadSubjectCards` → `_fetchSubjectCards` → `_finish` の順で、`_finish` の中で
`_buildChapterMap()` 等が `requestAnimationFrame` 越しに走る。**演出の終わりをここに合わせること**
（先に演出が終わると、まだカードが並んでいない画面が見える）。

### B2. 進捗バーの「距離感」【最優先】

`study_exam.js` の `_updateExamProg()` は**バーの幅が伸びて数字が跳ねるだけ**。
50問セッションだと、連続正解が切れている間（＝実力的に一番苦しい時間帯）は演出がゼロになる。

**⚠️ 設計上の決定：節目は「祝わない」。距離感を示すだけにする。**
連続正解（tier）と別軸で祝う演出を足すと tier 演出とぶつかり、画面が騒がしくなるため。

- 進捗バーに**目盛り**を打つ（半分・残り10問）。跨いだ瞬間に光が走るだけ。**音も粒子も出さない。**
- バー上に**難問（`data-rate < 60`）の位置を印として置く** ＝ 残りに何が待っているかが見える。
- 残り5問から盤面の色温度をゆっくり上げる（ラストスパート）。
  これは連続正解と独立した軸なので tier と競合しない。

⚠️ 難問の判定は `data-rate` が正本で、閾値は **`HARD_RATE = 60`**（`gamify.js` と study.html の
フィルタ「難問(<60%)」と同じ数字にすること）。**`data-rate` 属性が無い問題（正答率なし）は
難問に数えない**——出典に数字が載っていないだけで、難しいという意味ではない。

### B3. 結果画面の難問可視化

`showExamSummary()` に「難問 8問中 5問正解」を出す。
B2・B4 と**同じ `data-rate` 1本が経路を貫く**構成にすること（予告 → 道中の印 → 結果）。
「難しいところに挑んだ」という事実が3回別の形で返ってくる。

既存の A1（難問クリアの刻印）と世界観が揃う。

### B4. 開始モーダルの予告

`study.html` の `#examStartOv`。**開始を押すまで何問出るのか分からない**（分母は `startExam()` で確定）。

- 章チップ・フィルターを触るたびに「この条件で **N問**（うち難問 **M問**）」をリアルタイム更新。
  演出であると同時に情報。
- モーダル自体の入場アニメも無いので付ける。

### B5. 結果画面を閉じた後

`closeExamSummary()` は overlay を閉じて科目を読み直すだけ。余韻も次への導線もない。

- 閉じる動作に「幕が下りる」余韻。
- 戻った先で、今解いた問題が**成績付きで並び直す**（誤答が赤く残る）。今は普通のカードに戻るだけ。

### B6. 選択肢のシャッフルを見せる

「選択肢はシャッフルされます」はモーダルの文字でしか伝わっていない。
**1問目のカードだけ、選択肢が一瞬並び替わる動きを見せる。**
「毎回違う配置で来る」が体で分かり、暗記ではなく理解で解く感覚に繋がる。

⚠️ **下線部がある問題（`<u>`）はシャッフルされない**。この演出も出さないこと。

### B7. 1問目のカード入場を特別扱いする（小）

カウントダウン（C9）の直後、1問目の入場が2問目以降と同じ。開幕だけ登場を作る。

### B8. 誤答再試験を「リマッチ」として演出する（小〜中）

`retryWrongExam` は今、普通に始まる。落とした問題を相手に見立てた入り方にする。
既存の C2（RECOVER）と世界観が揃う。

## 4. Phase 3 — stats.html の再構成【減らす → 動かす】

### 4-1. 現状の診断（ユーザー確認済み）

セクションが **14本**あり、うち重複が2組ある。

**「弱いもの」のリストが4本：**
📐本番との差／💡取りこぼし問題／🎯苦手問題ランキング／🔍誤答選択肢パターン。
どれも uid 単位のリストで**同じ問題が複数に重複して載る**。
4本を見比べないと「次に何をやるか」が決まらない。

**「時間の記録」が3本：**
🗓学習カレンダー(12週)／📅30日間の学習記録／⏱30日間の学習時間。ほぼ同じ期間の同じ話。

**そのほか：**

- 🤖 AI相談用データが**ページの上から2番目**にある。道具であって情報ではない。
- `chartSec` / `gapSec` / `missSec` が `display:none` から出入りするので、
  **日によってページの形が変わる**。「あの表はどこだっけ」の原因。
- 🗺 章別ヒートマップが **180章**を一度に出している。
- 母数の扱い（`HM_MIN_N = 3`・薄いセルは「—」）は**既にきちんとしている。ここは触らない**。

### 4-2. 📐「本番との差」は廃止する

`renderGap()` の計算：

```js
const mr  = Object.entries(myrate).filter(([uid]) => isIn(uid));  // 自分が解いた問題だけ
const nat = Object.keys(RATE).filter(isIn).map(u => RATE[u]);     // その科目の全問
diff = (自分が解いた問題の正答率) - (科目の全問の本番正答率の平均)
```

**引き算の左右で分母が違う。**
左は「自分が試験モードで解いた問題」、右は「その科目の全問」。
難問フィルターで解いていればそれだけで差はマイナスに振れ、易問ばかりならプラスに出る。
**数字が何を意味するのか原理的に読めない**（ユーザーの「何を意味しているのか不明」は正確な直感）。

正しくやるなら**同じ問題集合で比べる**（自分が解いた uid の本番正答率の平均 vs 自分の正答率）。
**ただしその形は既に2箇所にある**——
「💡取りこぼし問題（本番正答率80%以上なのに落とした）」が uid 単位で同じことをやっており、
「本番正答率帯ごとの自分の正答率」（`bandRows`）が同じ軸をより丁寧に見せている。
作り直すと3つ目の重複になる。

→ **廃止し、弱点統合リストへ吸収する。**

### 4-3. 新しい構成（4層）

```
1. 今の状態
     済み / 連続🔥 / 今日の学習時間
     国試までの日数とペース（必要ペース vs 直近7日の実績）
     🔔 復習の見通し

2. 積み上げ
     🗓 学習カレンダー(12週) を主にする
     30日の解答数・学習時間は カレンダーのセルの内訳（既存 #calReadout）へ吸収
     ✅ 済みレベル分布 / 📈 科目別正答率の推移 はここ

3. どこが弱いか
     弱点リストを1本に統合（各行にタグ 🔻本番差 / 💡取りこぼし / 🔁反復ミス）
       ← 📐本番との差(廃止) / 💡取りこぼし / 🎯苦手ランキング / 🔍誤答選択肢パターン を合流
       ← 🔍誤答選択肢パターンは各行の詳細（展開）へ
     🩺 弱点カルテ（科目 × 設問形式）
     🗺 章別ヒートマップ → 科目を選んでから章、の2段にする

4. 道具
     🤖 AI相談エクスポート（末尾へ移動）
```

- `display:none` の出入りは、**空の状態を「まだデータがありません」で常設**して解消する
  （ページの形が日替わりで変わらないようにする）。
- **統合リストの各行から study.html へ直接飛べること**を必ず確認する
  （`study.html?sid=X&filter=weak` の経路が既にある）。

### 5-1. 衝突している前提（旧 §5-1 から維持）

- ハブ（index.html）＝ **真鍮・銅で固定**。テーマに振らない。
- 試験モード（study_exam.js）＝ **演出7テーマでランダムに配色が変わる**。

片方に寄せると、もう片方の意味が壊れる。→ **層を分ける。**

| 層 | 色 | 中身 |
|---|---|---|
| **筐体**（シャーシ） | **真鍮固定**。ベース6テーマにも演出7テーマにも振らない | 稜線・チャネル・リベット・レール |
| **盤面**（表示） | 可変。ベース配色の `--or` と、意味色 `--yl`/`--gr`/`--rd`/`--blu` | 進捗の塗り・数字・スコアリング・難問印・粒子 |

**ハブのゲージが既に採っている分け方**（真鍮の歯車 ⇔ `--or`／`--gr` の弧）と同じなので、新しい規約は増えない。

#### ⚠️ `.qc` には何も足さない（D8 で正式に却下）

理由は3つ。

1. **層が無い。** `::after` は既に2人が使う。同時には立たない
   （cleanup が `exam-multi-correct` を外してから `_applyRecapChipsSoon` が

2. **枚数。** カードは最大594枚（神経）DOMに載る。全枚数に疑似要素と `background-image` を足すのは
   iOS のタイル描画に効く（`content-visibility` の件と同じ土俵）。
3. **意味。** カードは「問題」であって「計器」ではない。筐体はカードの外側にあるべき。

#### D4. 開始モーダルの筐体

⚠️ **2026-08-19 に実装手段を疑似要素から要素本体へ変更した。** 理由は次項（スクロールで流れる）。

| | |
|---|---|
| **どこに** | `.exam-start-box` **本体だけ**。`border` / `background-image` / `box-shadow` の3つ。**疑似要素は使わない** |
| **何を** | ①枠を琥珀の即値から真鍮固定へ ②四隅のリベット4点 ③内側の稜線 |
| **いつ** | 静的。**筐体だけの入場アニメは持たない**（箱ごと `examBoxIn` でスケールインするので、塗ってある筐体も一緒に入る） |

##### ⚠️ 疑似要素で描いてはいけない — `overflow-y:auto` の中では流れる

`.exam-start-box` と `.exam-modal` は**どちらも `overflow-y:auto`**（章チップや科目別テーブルが伸びるため）。
スクロールコンテナの中に置いた `position:absolute` の疑似要素は**内容と一緒にスクロールする**ので、
章チップを下まで送ると**リベットと稜線だけ上へ流れて消える**。

`background-image`（既定の `background-attachment:scroll`）と `box-shadow:inset` は
**ボーダーボックスに固定されて流れない**。だからこの2つで描く。

副産物が2つある。**どちらも設計を軽くする方向:**

1. **入場アニメが要らなくなる。** 筐体が箱そのものに塗られているので、`examBoxIn` の
   スケールインに自動的に乗る。`.open` 配下の限定も不要。
2. **`.exam-start-box` / `.exam-modal` の疑似要素2層が空いたまま残る**（5-3 の表を更新済み）。

##### 描き方

- 枠: `border:2px solid rgba(255,154,60,.45)` → `border:2px solid var(--exam-brass)`。

#### D9. 稼働灯 — カードに向かっている間だけレールが流れ、答えた瞬間に消える

**2026-08-19 追加。** 元の 5-6 は「筐体は完全に静止」だったが、**それだと Phase 2 が
自分で見つけた穴（§3 B2「連続正解が切れている間＝一番苦しい時間帯は演出がゼロ」）を
埋め損ねる**ことが分かったので、動きを1つだけ足す。

| | |
|---|---|
| **どこに** | `.st-hdr::after`（D3 のレールの上を走る光）。⚠️ **D3 のレールは `::before` へ移す**（下記） |
| **何を** | レールの上を左から右へ走る細い光。1本走り切る尺で無限ループ |
| **いつ点く** | いま取り組んでいるカード（`.exam-key-focus`）がある間 |
| **いつ消える** | ①解答した瞬間（`exam-revealed` になった）から `EXAM_IDLE_BEAT_MS` の間 ②取り組み中のカードが無いとき ③`_fxOff()`（reduced-motion） |

##### なぜ「読んでいる間」なのか

ユーザーの実際の解答は速く、**同じカードに20〜30秒留まることはほとんど無い**。
つまりこの経路の空白は「長く稀」ではなく **「短く頻繁」**（1問あたり8〜15秒程度で、
そのうち演出が占めるのは1〜2秒）。したがって:

- **50問セッションでは「動く／止まる」が50回**繰り返される。連続した霧ではなく、
  **ユーザー自身の解答が刻む拍**になる。これが Phase 4 の中で唯一「時間」を持つ演出になる。
- 止まりが読めるのは、動きが**その直前まで確かにあった**からで、
  静止を既定にしていた旧 5-6 では作れない効果。

⚠️ **周期を長くしないこと。** 空白が8〜15秒しかないので、4〜6秒の「呼吸」だと
**1周も回りきらずに毎回途中で止まる＝ちらつきに見える**。
`--exam-idle-cycle` の既定は **1.4s**（光が1本走り切る尺）。ここは短い側に倒す。

##### 実装 — フックは `_updateExamFocus()` の1か所だけ

`_updateExamFocus()`（study_exam.js 3565行付近）が**既にこの状態を計算している**。
`.exam-revealed` でない可視カードのうちヘッダ下端より下の最初の1枚を「いま取り組んでいるカード」
として `.exam-key-focus` を付け替えるだけの関数で、**10箇所から呼ばれている**——
816／3783（開始）・881／918／932／3343／3357／3385（**解答直後・3経路すべて**）・3572（スクロール）。

⚠️ **`_afterCorrectFx` にも `_tallyQuestion` の3箇所にも書かないこと。**
前者は**複数選択の経路を通らない**（CLAUDE.md に明記）。後者は3箇所に散る。
`_updateExamFocus` なら**1関数で全経路を覆え、取りこぼしが構造的に起きない**。

必要な状態は3つの定数と2つの変数だけ:

```
EXAM_IDLE_DELAY_MS = 0      // カードに向かってから点灯するまでの遅延。★既定0（下記）
EXAM_IDLE_BEAT_MS  = 1200   // 解答してから再点灯するまでの「一息」。解答演出とほぼ同尺
--exam-idle-cycle  : 1.4s   // 光が1本走る尺（CSS 側）
_examIdleTimer     = null   // 点灯待ちのタイマー。★必ず1本だけ
_examIdleHoldUntil = 0      // この時刻までは点けない（解答直後の一息）
```

`_updateExamFocus()` の末尾でやること:

1. `_fxOff()` なら消灯して即 return（reduced-motion）。
2. **直前まで焦点だったカードが `exam-revealed` になっていたら**
   `_examIdleHoldUntil = Date.now() + EXAM_IDLE_BEAT_MS` を立てて消灯する。
   ＝これが「答えた瞬間に止まる」。
3. 取り組み中のカードが無ければ消灯。
4. あれば、`_examIdleHoldUntil` と `EXAM_IDLE_DELAY_MS` の遅い方まで待ってから点灯。

⚠️ **タイマーは常に1本。** 張り直す前に必ず `clearTimeout` する。
`_armHold`（gamify.js）・`_startGaugeAmbient`（index.html）と同じ約束で、
**再描画のたびに `setTimeout` を積むと多重に発火する**という前科が2件ある。
`_updateExamFocus` はスクロールのたびに走る＝この経路で一番呼ばれる関数なので、
ここを守らないと確実に踏む。

⚠️ **cleanup（study_exam.js 3820行付近・`body.exam-mode` を外す所）で、
点灯クラスとタイマーの両方を落とすこと。** クラスが残ると通常閲覧のヘッダで光が走り続ける。

##### ★ 遅延（`EXAM_IDLE_DELAY_MS`）は可変にして既定0

**既定は 0**＝カードに向かった瞬間から点く（ユーザー判断・2026-08-19）。

ただし**定数のまま残し、値だけで挙動が変わる形にしておくこと**。理由:
解答速度によって体感が正反対に振れるためで、実測してから決めたい。

| 1問あたり | 遅延0（既定） | 遅延を入れた場合 |
|---|---|---|
| 約10秒 | 10秒動いて1秒止まる＝拍が読める | 末尾の数秒だけ＝短すぎて読めない |
| 約6秒 | 点滅に近くうるさい可能性 | ほぼ静止。**速答した問題では一度も点かない** |

倒す先の候補は **`FAST_TIER_MS[2] = 7000`**（A3 の速答3段の下限＝「速答ではない」の境目）。
ここを再利用すると **A3 が褒める区間は静かで、褒めない区間だけ機械が回る**という筋が通り、
しかもユーザーの速度に自動で合う。**新しい定数を作らずに済む。**

⚠️ **分布は `mec_attempts_v1` に所要秒として残っている**（弱点カルテの素材）。
「1問あたり何秒か」は推測せず、実機の localStorage から読んで決めること。
ログは端末側にあるのでリポジトリからは見えない——stats.html の「🤖 AI相談用にコピー」か
DevTools の `MecAttempts` から出す。**これは Phase 4 の宿題として残っている唯一の未確定値。**

##### 消し方は `opacity`。`animation` の付け外しも `animation-play-state` も使わない

- **animation は掛けっぱなしにして、`opacity` だけを body のクラスで出し入れする。**
- ⚠️ **クラスで `animation` ごと外すと、`transform` が基準値へ戻って光が始点へ飛ぶ**
  （`.ep-sweep` で「fill を付けない animation は終わると基準値へ戻る」を実機で踏んでいる。
  あそこでは静止位置を書いて回避したが、ここは走行中に消えるので同じ手が使えない）。
- ⚠️ **`animation-play-state:paused` は使わない。** 光がレールの途中で凍りつき、
  「止まった」ではなく「固まった」に見える。
- 消灯は `transition:opacity 180ms` で受ける。再点灯は位相を気にしない
  （無限ループなので、途中から現れて問題ない）。
- 掛けっぱなしのコストは 1px の疑似要素1つの `transform` ループ＝無視できる。
  非表示タブではブラウザが CSS アニメーションを間引くので、
  **`_tweenNum` が rAF で0のまま凍った型の事故はここでは起きない**（CSS アニメーションなので）。

##### D3 との層の分担（D3 を1点だけ修正する）

| 層 | 中身 |
|---|---|
| `.st-hdr::before` | **レール本体（D3）** ← `::after` から移す |
| `.st-hdr::after` | **稼働灯（D9）** |
| `.st-hdr` 本体 `animation` | 空きのまま（使わない） |

理由: 疑似要素は `::after` が後に描かれるので、**レールを `::after` に置くと光がレールの下に隠れる**。
`z-index` で捻じるより、最初から順番どおりに割り当てる方が壊れにくい。
**これで `.st-hdr` の層は満杯になる**（5-3 の表を更新済み）。

##### ラストスパート（`epSprint`）との関係

残り5問から `.exam-prog` が脈打つが、**稼働灯はヘッダのレール＝別要素・別の意味**
（レール＝「あなたを待っている」／ベイ＝「もうすぐ終わる」）なので**そのまま両立させる**。
層の競合も無い。

⚠️ ただし実機（5-9 の段5）で「うるさい」と感じたら、
`body.exam-sprint .st-hdr::after{opacity:0}` の1行で消せる形にしておくこと。
**その逃げ道があること自体を実装時に確認する**（後から探すと配線を追い直すことになる）。

##### reduced-motion

`_fxOff()` が真なら**点灯クラスを一度も付けない**（JS 側で止める）。
CSS 側も vars.css の `@media (prefers-reduced-motion:reduce)` が
`*::before,*::after` の `animation-duration` を潰すので二重に止まる。

⚠️ §6 の「消えるだけにしない」は満たされている——**光が消えてもレール（D3）は残る**ので、
「筐体がある」という事実は静的な印で出続ける。稼働灯は情報を持たない付加物であって、
これが無いと読めなくなる情報は1つも無い。

**テストで守れること:**
①点灯クラスを付け外しする箇所が `_updateExamFocus` と cleanup の2か所だけ
②`EXAM_IDLE_DELAY_MS` の既定が `0`
③`setTimeout` と `clearTimeout` が対で存在する（タイマー1本の担保）
④cleanup で点灯クラスとタイマーの両方が落ちる
⑤`_fxOff()` を通している
⑥レールが `.st-hdr::before`・稼働灯が `.st-hdr::after`（層の分担）
⑦稼働灯の宣言に `animation-play-state` が無く、点灯クラスの側は `opacity` だけを切り替えている
⑧`body.exam-sprint` で消せる逃げ道が1行で書ける形になっている（＝稼働灯が単独のセレクタで指せる）

### 5-5. ヘッダの高さは1pxも増やさない【最優先の不変条件】

`.st-hdr` は iPad で約180px あり、`_fxBand()` がその**下端**を演出の焦点の基準にしている

**許容量: ±0px。** 1px も増やさない。守り方は3つだけ:

1. 筐体は**既存の `padding` / `border` の内側**にだけ描く。
2. 面ではなく `position:absolute` の疑似要素で描く（フローに出ない）。
3. 触ってよいのは `background` / `box-shadow` / `border-*color*` の3つ。

つまり試験中もフィルターパネル（科目チップ23個＋難易度＋検索＋章ジャンプ）が
畳まれていなければヘッダに載っている。ここを「試験中は隠せば高さが減る」と考えるのは
**Phase 4 の範囲外**（情報を削る変更であり、意匠の話ではない）。やるなら別提案として立てる。

### 5-6. 動くのは「稼働灯」1つだけ（2026-08-19 に方針を1段だけ緩めた）

**筐体は原則として静止。** 自前の `animation` を持つのは**稼働灯ただ1つ**。

| 動くもの | 尺 | 意味 |
|---|---|---|
| **稼働灯（D9）** | `--exam-idle-cycle` 1.4秒のループ | 「機械があなたを待っている」＝**取り組み中であることそのもの** |
| （モーダルの筐体） | — | **自前のアニメを持たない。** 箱ごと `examBoxIn`（0.32秒）でスケールインするので、塗ってある筐体も一緒に入る（D4） |

**それ以外は1つも動かさない。** 呼吸・回転・光沢の往復といった「理由のない常時アニメ」は D8 で却下済み。

#### 旧方針（完全静止）を1段だけ緩めた理由

策定時は「試験中の筐体は完全に静止」としていた。挙げた理由は3つで、**うち2つは今も有効、1つは誤りだった**。

| 旧理由 | 今の評価 |
|---|---|
| ① Phase 1 の「集中を切らない」と揃える | **過剰適用だった。** Phase 1 の決定は全画面セレモニーが**解答の瞬間を奪う**ことへの対処で、周辺視野のごく緩い動きは別カテゴリ。稼働灯は解答の瞬間には**消えている**ので、むしろ Phase 1 の思想に沿う |
| ② 層が競合する（`.exam-prog` の本体 `animation` は `epSprint` が使う） | **有効。** だから稼働灯は計器ベイではなく**ヘッダのレール**に置く（D9） |
| ③ 意味が濁る（理由なく動くものが増えると全部の動きが弱くなる） | **有効。だから動くものを1つに限る。** 稼働灯は「いまカードに向かっている」という状態そのものを持つので、理由のない動きではない |

そして緩めた決め手は、**静止のままでは §3 B2 が自分で見つけた穴を埋め損ねる**こと——
「50問セッションだと、連続正解が切れている間（＝実力的に一番苦しい時間帯）は演出がゼロになる」。
その空白の正体は**問題文を読んでいる時間**であり、そこはこの経路で唯一まだ何も無い区間だった。

#### reduced-motion / 非表示タブ / 画面外の扱い

- **JS のガードは稼働灯の1か所だけ**（`_updateExamFocus` の先頭で `_fxOff()` を見る・D9）。
  D1〜D8 は CSS だけなので、ガードは要らない。
- 稼働灯のループ（と、筐体が乗る `examBoxIn` の 0.32 秒）は、vars.css の
  `@media (prefers-reduced-motion:reduce){ *,*::before,*::after{animation-duration:.01ms!important} }`
  が**全ページに当たっている**ので CSS 側でも自動的に止まる（JS のガードと二重）。
- **非表示タブ・画面外の停止条件は要らない。** 稼働灯は CSS アニメーションで、
  ブラウザが背景タブで間引く。**rAF が止まって数字が0のまま凍った型の事故
  （`_tweenNum`・`countUp`）はここでは起きない。**
  加えて、点灯を駆動する `_updateExamFocus` はスクロールと解答でしか呼ばれないので、
  裏に回ったタブでは状態自体が動かない。
- ⚠️ §6 の「reduced-motion で消えるだけにしない」は満たされる。
  **稼働灯が消えてもレール・稜線・リベット・チャネルは全部そのまま見える。**
  むしろ Phase 4 の大半は、動きが消えた画面に残る静的な意匠として効く。
- ⚠️ 用語の訂正: **study_exam.js のガードは `_fxOff()`（reduced-motion のみ）で、
  `_fxOk()`（非表示タブも見る）は index.html にしか無い。**
  D9 で通すのは `_fxOff()` の方。実装セッションが `_fxOk()` を探して回らないように書いておく。

### 5-7. ベース配色6種との相性 — 稜線で担保し、テーマ別の分岐は作らない

**心配していたこと:** 琥珀の書斎（`--bg-g1:#281614`）と薔薇（`#301423`）は暖色なので、
真鍮が地に同化するのではないか。

**実測（`--exam-bevel-hi` を各テーマの `--bg-g1` に重ねた色と、地とのコントラスト比）:**

| テーマ | `--bg-g1` | α=.30 | α=.34 |
|---|---|---|---|
| 深夜のインディゴ（既定） | `#0D0541` | **1.87**（最小） | **2.09**（最小） |
| 炭 | `#17191E` | 2.05 | — |
| 深緑 | `#0D2018` | 2.03 | — |
| 深海 | `#08202A` | 2.02 | — |
| 琥珀の書斎 | `#281614` | 2.06 | — |
| 薔薇 | `#301423` | 2.01 | — |

**結論が2つひっくり返った:**

1. **一番弱いのは暖色テーマではなく既定のインディゴだった。** 暖色は「同化しそう」に見えるが、
   輝度で見ると `#281614` は `#0D0541` より暗く、稜線はむしろ**よく見える**。
2. **6テーマの散らばりが 0.19 しかない。** → **テーマ別の微調整は作らない。**
   `html.th-amber` / `html.th-rose` の上書きブロックは**1つも書かない**。

**したがって α は .34 を採る**（既定テーマでの床が 1.87 → 2.09 に上がり、余裕ができる）。
**しきい値は「全6テーマで 1.9:1 以上」**とし、テストが実測する（5-8 の項目6）。

##### 暖色テーマで本当に効くのは「対の暗線」

輝度は足りているので、暖色で心配なのは**色相の同化**（真鍮のオークルが琥珀の地と同じ色域）。
これに効くのは真鍮の色をいじることではなく、**`--exam-bevel-lo`（無彩色の黒 .45）を必ず対で置くこと**。

- 明線だけだと「地が少し明るい帯」に見える。**明線＋暗線の対**になって初めて「縁」＝金属に見える。
- 黒は6テーマすべてで中立なので、**対の片側が常にテーマに依存しない**。
- ⚠️ **`--exam-bevel-lo` を「見えないから」と省かないこと。** これが Phase 4 の唯一の技術的な要。
  省いた瞬間に暖色テーマで意匠が消える。

##### 地の取り方（テストの根拠）

テストは `--bg-g1` を地として計算する。実際の筐体の下は
`.st-hdr`＝`rgba(var(--hdr-rgb),.94)`、`.exam-prog`＝さらに `rgba(0,0,0,.5)` と**もっと暗い**。
`--bg-g1` は**最も明るい地＝最悪ケース**なので、これで通れば実機は必ず通る。

##### テーマが振る「角丸」「影」との折り合い

- `html.th-amber` は `--r-sm:3px / --shadow-card:none`（紙のように平ら）、
  `html.th-rose` は `--r-lg:24px`（大きく丸い）。
- ⚠️ **筐体はこれらを参照しない。** `.exam-start-box` / `.exam-modal` の
  `border-radius:20px` は即値で、テーマで振っていない。**振らせないこと**——
  リベットの位置（角から10px内側）は角丸の半径に依存しており、`--r-lg` を参照すると
  薔薇（24px）でリベットが角丸の外へ出る。

### 5-10. 出荷 — `sw.js` の `SHELL_VERSION` を bump しないと端末に届かない

**⚠️ これを忘れると「実装したのに iPad で何も変わらない」になる。**

`study.css` も `study_exam.js` も **`sw.js` の `SHELL` に入っている**（sw.js 204行付近）。
Service Worker が旧版をキャッシュから返すので、ファイルを push しただけでは端末は更新されない。

| 定数 | Phase 4 での扱い |
|---|---|
| `SHELL_VERSION`（現 `"2026-08-19a"`） | **必ず bump する。** この文字列を変えると sw.js のバイトが変わって SW 更新が走り、`install` が `cache:'reload'` でシェル（html/css/js）だけを取り直す |

- 段ごとにコミットするなら、**`SHELL_VERSION` は最後の1回だけ bump すればよい**
  （実機確認のために各段で確かめたいなら、その都度 bump しても害は無い＝シェルだけの再取得なので軽い）。
- sw.js の冒頭は変更履歴のコメントが積まれている。**「シェルのみの変更なので CACHE は据え置き＝
  SHELL_VERSION だけ bump」という定型行が既に8本ある**ので、同じ形で1行足す。

#### 版数バッジ（`#mecBuildVer`）は更新しない ← 2026-08-19 決定（案B）

`study.html` の `#mecBuildVer`（現 `b-0725a`）は「新版が届いた証拠」を目視するためのものだが、
**Phase 4 は `study.html` を1行も触らないので更新されない。**

これは**意図どおりに据え置く**。理由:

- Phase 4 は**見た目が変わる変更**なので、「筐体が見えるか」がそのまま到達確認になる。
  バッジという間接的な証拠を使う必要が無い（構造的に自己証明する）。

## 6. 全フェーズ共通の制約（既存の規約・破ると壊れる）

- **発火位置は `_fxBand()`（study_exam.js）が正本。** `window.innerHeight * 0.4` のような
  画面基準の座標を新しく書かない。
- **`document.body` を transform しない。** transform された要素は `position:fixed` の
  包含ブロックになるため、揺れている間だけ全演出がページ先頭基準になって画面外へ飛ぶ。
  画面を揺らすなら `_shakeFxLayers()`。
- **正解／誤答の追加演出は `_afterCorrectFx` / `_afterWrongFx` へ足す。**
  正解の経路は2つある（`revealAnswer`＝選択肢／`_revealCalcAnswer`＝計算問題の桁入力）ので、
  片方に直接書くと**計算問題50問だけ演出が抜ける**。
- **`fx_engine.js` のエミッタ追加は常に純増で行う。** 既存関数の引数や既定値を変えると7テーマ全部に波及する。
  位置を自前で持つ型は **`STATIC_TYPES` に登録必須**（忘れると重力で1フレームで消える）。
- **1要素で使える層は3つだけ**（本体の `animation` / `::before` / `::after`）。
  同じ層に2つ置くと後勝ちで片方が黙って死ぬ。
- **tier で配列・マップを引くときは `_tIdx(tier, o)` を使う**（`Math.min(tier, 6)` を新しく書かない）。
- **reduced-motion（`_mecReducedMotion()` / `_fxOk()`）を必ず通す。** 常時ループは
  非表示タブ・画面外でも止める。
- **`prefers-reduced-motion` 時に「消えるだけ」にしない。** 動きの代わりに静的な印（色・字・枠）で
  同じ事実を出す（ハブは既に二重化してある）。優先度は低いが設計としては守る。

# 11. Phase 5 — 読んでいる間の演出（2026-08-19 策定）

## 11-0. 何が問題か

正解時・連続正解時の演出は厚いのに、**解答するまでの 8〜15 秒がほぼ無演出**である。
策定時に現物を数えたところ、読書中に存在するのは次の2つだけだった。

| 現物 | 実装 | 実寸 |
|---|---|---|
| 焦点カードの枠 | `.qc.exam-key-focus`（study.css:167） | 3px の `--yl` outline ＋ 薄い glow。**完全に静止** |
| 稼働灯 | D9（`.st-hdr::after`） | **高さ 1px** の光が 1.4 秒周期で走る |

つまり読書中の演出は事実上「1px の光 1 本」で、Phase 4 が薄いという指摘と同じ根を持つ。

**この節の中心的な読み替え**——読書時間は「無」ではなく **「機械が待っている時間」** である。
D9 のコメントは既に「機械があなたを待っている」と書いており概念は正しかった。**1px で実装したのが誤り**。
しかもこれは steampunk と相性が最も良い。steampunk の本質は稼働中の華やかさではなく
**アイドリング中の機械**（圧が溜まる・歯車が空回りする・弁から蒸気が漏れる）だからである。

## 11-1. 5つの原則【破ると「派手だが解けない」画面になる】

⚠️ **読書中の演出は、他のどの演出とも性質が違う。読解の邪魔になりうる唯一の演出である。**
正解時の演出は読み終わった後なので何をしてもよいが、ここは違う。

1. **中心視野に置かない** — ヘッダ・カードの縁・画面端（周辺視野）だけ
2. **文字の上に何も重ねない**
3. **周期を一定にする** — 不規則な動きは注意を奪う（D9 が 1.4 秒固定なのは正しい）

## 11-4. 段1 — 焦点まわり（土台）

### 11-4-0. 先に塞ぐ穴 — 試験開始直後だけ焦点が付かない【必須】

`startExam` の `requestAnimationFrame(_updateExamFocus)`（study_exam.js:816）は
**カードが出そろう前に1度走るだけ**で、次に走るのは最初のスクロールか解答である。
そのため開始直後は `.exam-key-focus` が誰にも付いていない。

2026-08-19 に「稼働灯が点かないだけ」として**許容と判断した穴だが、Phase 5 で判断を覆す**。
R3・R5・R13 がすべて焦点状態にぶら下がるので、放置すると**1問目だけ演出が丸ごと抜ける**。

- **直し方** — `startExam` 末尾の `setTimeout(..., _cdEnd + 60)`（B6/B7 が1問目を立ち上げる場所）で
  `_firstCardEntrance` の直前に `_updateExamFocus()` を呼ぶ。カウントダウンが明けた後なので
  カードは出そろっており、**既存の3経路（開始・スクロール・解答）を1つも変えない**。
- ⚠️ `_getExamTargetCard()` の条件は変えないこと。ここを触ると解答直後の焦点移動が壊れる。

### 11-4-1. R13 — 焦点カードを持ち上げる

いまの `.exam-key-focus` は `outline` と平たい glow だけで、カードが**手前に出てこない**。
`box-shadow` を深い落ち影に差し替えて物理的に持ち上げる。

- ⚠️ **`.qc` の既存 `box-shadow`（`0 4px 24px` ＋ inset ハイライト）を消さずに積むこと。**
  消すとカードが平らになり、`.qc:hover` でも失われる（B5 で同じ注意を書いている）。
- R5 と同じ `box-shadow` の作業なので実質タダで乗る。

### 11-4-2. R5 — カードが「装填される」（真鍮のクランプ）

焦点が移った瞬間、カード左端で真鍮のクランプが**カチッと閉じ**、解答すると開いて離す。

- ⚠️⚠️ **`.qc::before` を使ってよい。** CLAUDE.md は「`.qc` の層は満杯」と書いているが、
  正確には**状態で排他**になっている:
  - `.qc.exam-scar::before`（C5 の傷）が付くのは **`exam-revealed` のカードだけ**
  - `.exam-key-focus` が付くのは **`_getExamTargetCard()` が `!exam-revealed` で絞った未解答カードだけ**
  - ⇒ **同一カードに同時に載ることが構造的に起きない**。
  ただし**この排他は `_getExamTargetCard()` のフィルタが担保している**ので、
  あそこを触るときは必ずこの依存を思い出すこと。CSS 側は
  `.qc.exam-key-focus:not(.exam-revealed)::before` と明示して二重に守る。
- ⚠️ `.qc[data-recap]::after`（B5 の成績）と `.qc.exam-multi-correct::after` は `::after` 側。触らない。

### 11-4-3. R3 — 連続正解を読書中も生かす

いま tier のラベルは 2.4 秒で消え、残るのは 3px のコンボメーターだけ。
**読んでいる間ずっと焦点枠が tier の色を帯びる**ようにして、
「今5連続中で、これを落とすと崩れる」という緊張を視野の端に残す。C1（崩落）の伏線にもなる。

- 実装は **`body` に `--exam-focus-c` を1本置く**だけ。`_showStreakEffect` / `_updateComboMeter` と
  同じ場所で `theme.comboColors[_tIdx(tier, ...)]` を書き込み、`examStreak < 2` で `--yl` へ戻す。
- ⚠️ **tier で配列を引くときは必ず `_tIdx(tier, o)` を使う**（`Math.min(tier,6)` を新しく書かない）。
- ⚠️ 誤答で `examStreak` を 0 にする前に色を戻すと C1 の崩落と競合する。**色戻しは C1 の後**。

## 11-5. 段2 — 稼働灯まわり

### 11-5-1. R1 — 圧が溜まり、解答で放出する（蒸気）

読書が **`FAST_TIER_MS[2] = 7000ms`** を超えたら、レール両端の安全弁から蒸気が細く上がりはじめる。
**解答した瞬間に一気に放出**する（正解でも誤答でも）。

- **意味づけ** — 遅い＝罰ではなく **「熟考している＝圧が溜まっている」**。放出が報酬になる。
  読書中の演出が解答演出の**伏線**になるので、独立した飾りにならない（デザイン監査の基準を通る）。
- **しきい値に新しい定数を作らない。** `FAST_TIER_MS[2]` を再利用すると
  「A3 が褒める区間（〜7秒）は静かで、褒めない区間だけ機械が動く」という筋が通る。
  D9 のコメント（`EXAM_IDLE_DELAY_MS` の項）が既にこの再利用を提案している。
- **材料は全部ある** — `MecFX.steam(x,y,o)`（fx_engine.js:797）、経過時刻は
  **`_examCardSeenAt`（`_markCardSeen` が記録済み・速答判定の起点）**。新しい帳簿を持たない。
- **発生源** — `_examFxHeaderBottom()`（＝レールの y）と可視域の左右端。`_fxBand()` から取る。
- ⚠️ 量を増やさないこと。`count:3〜4`・`alpha:.28` 程度。原則1（周辺視野）と原則2（文字に重ねない）。
- ⚠️ `blend:false` を必ず渡す（加算合成にすると湯気ではなく発光体になる＝ハブのゲージで踏んだ罠）。

### 11-5-2. R8 — スクロールに機械が応答する

いまの稼働灯は一定速度で「待っている」だけ。**スクロール中だけ光が速くなり**、止まると戻る。
「待っている機械」から**「あなたの読みに追従する機械」**へ変わる。

- ⚠️⚠️ **`animation-duration` を書き換えてはいけない。** 走行中に duration を変えると
  進捗率が不連続に飛び、**光がワープする**。Phase 4 で「`animation` は掛けっぱなしにする」と
  決めたのと同じ理由。
- **正しい実装は `getAnimations({subtree:true})` で CSS アニメーション本体を掴んで
  `playbackRate` を書き換えること。** playbackRate の変更は位相を保つので飛ばない。
  ⚠️ 疑似要素のアニメーションなので `element.animate()` では作れない。`subtree:true` が要る。
  ⚠️ 掴めなかった場合は**何もしない**（機能低下で済ませる。例外を投げない）。
- 速さは `1 → 2.4` 程度、止まってから **600ms** かけて戻す。
- ⚠️ `_onExamScroll` は rAF で間引かれている既存の経路。**ここに重い処理を足さない**
  （スクロール中に一番呼ばれる関数）。playbackRate の代入1回に留める。

### 11-5-3. R10 — 離席するとスリープし、戻ると起動する

**60 秒**スクロールも入力も無ければ稼働灯を落として機械がスリープし、
動きを検知したら**起動シーケンス**（レールに光が一往復してから通常運転）を出す。

- ①戻ってきた時に「再開した」合図が入る ②放置中に無駄なアニメを回さない
- ⚠️ **「放置＝叱られている」に見せない。** 機械が休むだけ、という描き方に留める。
- ⚠️ **タイマーは `_examIdleTimer` とは別に1本（`_examSleepTimer`）持ち、張り直す前に必ず
  `clearTimeout` する。** `_armHold`・`_startGaugeAmbient`・D9 で同じ型の前科が3件ある。
- ⚠️ `exitExam` のクリーンアップで**スリープ状態のクラスとタイマーの両方**を落とすこと。

### 11-5-4. R2 — 歯車をアイドル回転させる

計器ベイの進捗トラックの両端に真鍮の歯車を置き、**読書中はゆっくり定速回転、
解答した瞬間に1拍止まってカクンと1歯進む**。進捗と噛み合うので純粋な飾りにならない。

- **Phase 4 で歯車を却下した理由③「試験中は静止させる」は、D9 で既に1段緩めてある。**
  同じ論法で覆す。理由①（実装が2本ある）は**3本目を作らず SVG を素で書く**ことで回避する
  （`_gearPath` は index.html のローカル関数で study からは呼べない。共有すると
  「ハブは触らない」の約束が壊れる＝Phase 4 の判断を維持）。
- ⚠️⚠️ **ヘッダの高さを 1px も増やさないこと**（`_fxBand()` の焦点が動く＝§5-5 の最優先の不変条件）。
  `.exam-prog` は `padding:4px 14px` ＋ `font-size:11px`・`line-height:1.7` の span を含むので
  **行の高さは既に約 19px** ある。**13px の歯車はこの中に収まる**＝行は伸びない。
  ⚠️ 実装時に `.exam-prog` の実測高さを before/after で確認すること。1px でも増えたら**歯車を捨てる**。
- ⚠️ 歯車は**筐体**なので真鍮固定。テーマにも tier にも振らない。

## 11-6. 段3 — IntersectionObserver を1本立てる

### 11-6-0. 共有インフラ【最初に作る】

⚠️ **このプロジェクトには IntersectionObserver が1つも存在しない**（策定時に `grep` で0件を確認）。
R7・R9・R6 が3つとも要求するので、**observer は1本だけ作って共有する**。

- ⚠️⚠️ **全カードを observe してはいけない**（最大 594 枚）。
  **焦点カードが変わった時に、前のカードの対象を `unobserve` し、新しいカードの
  `.qimg` と最初の `.ch2` だけを `observe` する**。監視対象は常に数個に収まる。
- 生成は遅延（試験開始時）、破棄は `exitExam` で `disconnect()`。⚠️ **通常閲覧へ持ち越さない。**
- ⚠️ `content-visibility:auto` が `.qc` に載っているので画面外のカードは描画されない。
  observer の `rootMargin` を大きく取ると描画を強制することになる。**0 のままにする。**

### 11-6-1. R7 — 画像問題は「シャウカステン（読影灯）に掛ける」

医療画像が視野に入った瞬間、**真鍮の枠に嵌った状態から読影灯が点いて画像が浮かび上がる**。

- **この教材にしか無い意匠になる。** シャウカステン（X線読影灯）は steampunk と医療の交点にあり、
  借り物の語彙ではない。意味づけも自然で、画像は症例文とは別種の情報＝**証拠**。
- **技術的に有利** — 寸法は `image_dims.json` で予約済み＝**箱が先にあるので点灯前の枠を出せる**
  （レイアウトシフトが起きない）。`.qimg` は今 1px の枠と `cursor:zoom-in` があるだけ。
- ⚠️ **焦点カードの画像だけ**に限る（全科目で 2544 枚ある）。
- ⚠️ **拡大表示（`cursor:zoom-in` のクリック）と競合させない。** 演出は `pointer-events:none` の層で。
- ⚠️ 画像は `loading="lazy" decoding="async"`。**まだ読み込まれていない可能性がある**ので
  `complete` を見て、未完了なら `load` を待つ。⚠️ 失敗（`error`）でも枠が残らないようにする。
- ⚠️ **一度点けた画像は二度と点け直さない**（スクロールで往復するたびに光ると鬱陶しい）。
  `dataset` に印を付ける。

### 11-6-2. R9 — 「読む」から「決める」への相転移

長い症例文では選択肢は画面外にある。**選択肢が視野に入った瞬間＝決断フェーズに入った合図**として
稼働灯を止め、代わりに肢の側を生かす。読書と決断は別の作業なので、体で切り替わる。

- ⚠️ **稼働灯の停止は R10（スリープ）と経路を分けること。** 同じ `exam-idle-lit` を
  2箇所から落とすと、どちらが消したのか分からなくなる。**相転移は専用クラスで表す**。
- ⚠️ 相転移は**焦点カードについてのみ**判定する（下のカードの選択肢が見えても発火させない）。

### 11-5-1'. 【2026-08-19 追記】R1 の放出を2度にわたって拡大した（ユーザー要望）

**1度目**——「正解時も誤答時も煙はもっと大きくていい」。原因は**放出量を噴気の延長で決めていた**
こと。噴気は読書中なので原則1・2に縛られるが、**放出は読解がもう終わっている瞬間**なので
その制約は掛からない。放出側だけ約2.5倍（両弁 14→36粒・最大44→84px）にした。

**2度目**——「もっと大きく、画面中央まで吹き出して左右が重なってよい」。
左右の弁からそれぞれ**内側へ4段の小噴出**（計8点・64粒・最大110px）を撒く形にした。

- ⚠️⚠️ **到達距離は画面幅に比例させる**（`STEAM_SPAN = .42`）。固定 px にすると
  iPad(820〜1024) では中央を大きく越え、デスクトップ(1920) では全く届かない。
- ⚠️ **`MecFX.steam` の引数や既定値は変えない**（エミッタは純増の約束＝7テーマに波及する）。
  横へ伸ばすのは**同じ弁から x をずらして複数回呼ぶ**ことで作る。`steam` の `w` は左右対称に
  撒くので、弁1点で `w` を広げると画面外へ半分捨てる。
- ⚠️ **横へ届かせるのに速度を上げない**。`drag` は `Math.pow(drag, dt*60)` ＝ `.985` なら1秒で
  速度が約40%まで落ちる。届かせるのは**発生位置の分散**で作る。
- ⚠️ **`rise`（縦の初速）も上げない**。発生源はレール（実測 y≒209）で画面上端までの余地が
  それしかなく、上げると寿命1.0〜1.9秒の半分以上を画面外で使い「速く抜ける細い噴射」になる。
  実測: `rise:250` で画面内 0.38〜0.84秒／`rise:170` で 0.56〜1.23秒。
- 「発生源は2点のまま」という当初の自縛は**この要望で解いた**。ただし**弁が左右2つという
  筋書きは維持**する（8点はすべて2つの弁から内側へ伸びる列であって、独立した8つの弁ではない）。

### 11-5-4'. 【2026-08-19 追記】放出に合わせて歯車が膨らみ、火花が飛ぶ

同じ要望の後半。放出の瞬間に歯車が **3.2倍**（520ms）になり、噛み合いから**火花**が飛ぶ。

- ⚠️⚠️ **拡大は `scale` プロパティ。`transform:scale()` は使えない**——歯車は
  `animation:epGearSpin` が `transform` を占有しており、`transform` を別途宣言しても走行中の
  アニメーションに上書きされて**何も起きない**（黙って死ぬ型の失敗）。`scale` は独立プロパティ
  なので回転と合成される。
- **`scale` はレイアウトに影響しない**ので、ヘッダの高さも `.exam-prog` の高さも1pxも動かない
  （実測: 208.79px / 28.32px が拡大前後で不変）。§11-7 の条件1 を自動的に満たす。
- ⚠️ **倍率の上限は「右の歯車から画面右端までの約110px」**（タイマーと終了ボタンのぶんで
  画面幅に依らない）。超えると iOS Safari がレイアウトビューポートを広げ、2026-08-19 の
  ページ縮尺の振動が再発する。実測: 3.2倍で右端まで108px 残り、横スクロールも発生しない。
  はみ出してよいのは `.st-hdr` / `.exam-prog` / `body` / `html` がすべて `overflow:visible`
  だから（実測確認済み）。
- ⚠️ 火花は `MecFX.burst` に **`additive:false` を必ず渡す**（既定は加算合成＝光の玉になって
  金属片に見えない）。`shapes:['shard','square']` ＋ `gravity:1500` で弧を描いて落ちる。
- ⚠️ 歯車の膨らみは**放出とだけ連動**させる。読書中の噴気で膨らませると原則1・2に反する。

### 11-6-3'. 【2026-08-19 追記】R6 から「線」を全部落とした（ユーザー報告）

実装直後の実機で「**選択肢の一つ一つにある影が下線部のように見えて邪魔**」との報告。原因は
キーキャップらしさを出すために置いた **3本の水平線**（各肢の上端に明線 `inset 0 1px 0
--exam-bevel-hi`／下端に暗線 `inset 0 -1px 0 --exam-bevel-lo`／直下に硬い銅の側壁
`0 2px 0 --exam-copper`）。**肢は負マージンで詰めて積んである**ので、これらが
「各行に罫線が引かれた表」に見え、とくに銅の側壁が下線そのものに見えた。

⚠️⚠️ **これは見た目の好みでは済まない。下線部はこの教材では意味を持つ記号**である
——「本文中の下線部①〜⑤が選択肢そのもの」という問題が実在する（整形外科 NO.167・171・142／
放射線科 NO.2）。装飾の線がそこに紛れると設問の読解を壊す。

- **直し方**: `box-shadow` を **拡散した影1層（`0 3px 8px -3px`）だけ**にし、`inset` を廃止。
  **負の spread** が影を要素より内側へ縮め、左右の端で線状に伸びるのを防ぐ。
  立体感は「硬い線」ではなく **拡散した影＋わずかな浮き（`translateY(-1px)`）** で出す。
- ⚠️ Phase 4 §5-7 の「明線と暗線は必ず対で置く」は**面と縁を持つ筐体の話**であって、
  **文字が並ぶ行に適用してはいけない**。行に適用すると縁ではなく罫線になる。
- 副作用として R6 から真鍮が消えた＝名前どおりの「真鍮のキーキャップ」ではなくなったが、
  **選択肢は筐体ではないので真鍮を入れない方が分類としても正しい**。
- テスト `test_exam_reading.js` 項目27 が「縦オフセットがあるのに blur が 0」の層と `inset` を禁じる。
  ⚠️ 長さは `0` のように**単位無しで書かれる**ので `0px` 決め打ちの正規表現では硬い線を見逃す
  （実際に一度見逃し、旧CSSで検算して気づいた）。

### 11-6-3. R6 — 選択肢を真鍮のキーキャップにする

行頭の a〜e を「押す機械のキー」に見せる。**単体では静的で弱いので R9 と必ず組む**
——決断フェーズに入った瞬間にキーキャップが起き上がる。

- ⚠️ `.ch2` は `padding:2px 5px; margin:-2px -5px` で**負マージンで詰めてある**。
  ここを変えると `.exam-selected` / `.exam-instant-correct` の背景の当たりがずれる。
- ⚠️ **選択肢のラベル文字（`ａ`〜`ｅ`）は `.ch2` のテキストの一部**であって独立要素ではない。
  疑似要素で被せる形にすること。⚠️ 計算問題（`MecCalc`）には `.ch2` が無い＝**何も出ない**のが正しい。
- ⚠️ iPad には hover が無い。**hover 前提の演出にしない。**

## 11-7. 全段に共通の不変条件

| # | 条件 | 破ると |
|---|---|---|
| 1 | **ヘッダの高さを 1px も増やさない** | `_fxBand()` の焦点が動く（§5-5） |
| 2 | **筐体（真鍮）は tier にもテーマにも振らない** | Phase 4 の前提が消える。R3 が色を持つのは**盤面側の焦点枠**であって筐体ではない |
| 3 | **`_fxOff()`（reduced-motion）で全部止まる** | 静止画に戻るだけで情報は1つも失われないこと |
| 4 | **`exitExam` で全部落とす** | 通常閲覧へ持ち越す（D9 で踏んだ） |
| 5 | **タイマーは種類ごとに1本、張り直す前に `clearTimeout`** | 多重発火（前科3件） |
| 6 | **`body` を transform しない** | `position:fixed` の包含ブロックになり全演出が飛ぶ |
| 7 | **箱の外へ出る要素を作らない** | iOS Safari がレイアウトビューポートを広げ、**ページの縮尺が振動する**（2026-08-19 の実害） |
| 8 | **`.qc` / `.st-hdr` / `.sgh` に `backdrop-filter` を足さない** | iOS WebKit の合成が破綻して画面下が白くなる |
