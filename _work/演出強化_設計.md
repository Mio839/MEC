## 2. Phase 1 — セレモニーの交通整理【不具合修正を含む・最初にやる】

### 2-1. `ceremony()` にキューが無い（実害のあるバグ）

`gamify.js` の `ceremony(html, opts)`：

```js
ov.innerHTML = '<div class="gm-cer">' + html + '</div>';
ov.classList.add('show');
```

**上書きするだけでキューが無い。** 近接して2つ発火すると、先に描いた方は誰にも見られないまま消える。

しかもこれが起きる条件が「40問目」そのもの：

```
onAnswer()
  └ _bumpMission()  → _checkMissionCompletions() → ceremony('MISSION COMPLETE')
  └ _afterEvent()   → _checkLevelUp(true)        → ceremony('LEVEL UP')   ← 上書き
```

**同じ同期呼び出しの中で連続する。** 日次ミッション達成とレベルアップが重なる解答では、
MISSION COMPLETE は一瞬描かれて即座に消える。

`ceremony()` を呼ぶのは4か所（レベルアップ／章制覇／科目制覇／ミッション全達成）。
**`toast()` は既に `_toastQ` + `_drainToast()` でキューを持っている**ので、同じ作りにする。

### 2-2. `_afterEvent` が `examMode` を見ていない

```js
function _afterEvent(uid) {
  _statsCache = null;
  _updateHeaderChips();
  _checkLevelUp(true);        // ← 試験中でも全画面セレモニー(2.4秒)が出る
  _checkAchievements(true);
  if (uid) { _checkChapterClear(uid); _checkSubjectClear(uid); }
  _rerenderHubPanel();
}
```

`_microLapFx` と `_lapMilestoneFx` は先頭で `if (examMode) return;` しているのに、
**一番大きい全画面セレモニーだけが素通し**。試験の tier 演出の真上に被る。

### 2-3. 実装方針

1. `ceremony()` をキュー化する（`toast()` と同型。順に再生し、前のものが消えてから次を出す）。
2. **試験中に発生したセレモニーは溜めておき、結果画面（`showExamSummary`）で順に再生する。**
   - tier 演出との衝突が消える。
   - 結果画面が「この1本で何を達成したか」の場になる＝**外した自己ベスト・前回比の穴がここで埋まる**。
   - データ追加ゼロ。
3. 実績（`_checkAchievements`）は `toast()` 経由でキュー済みなので、そのままでよい。
   ただし**試験中はトーストも溜める**かは実装時に判断する（トーストは小さいので出しても害は小さい）。

⚠️ **`gamify.js` は study.html でも読み込まれている**（`<script src="gamify.js">` が script 一覧にある）。
ハブ専用ではないので、study.html 側で発火することを前提に組むこと。

⚠️ レベルアップが「上がったその場」ではなく結果画面で出ることになる。
**これはユーザーが承諾済みの仕様変更**（集中を切らないことを優先）。

### 2-4. テスト

`_work/test_gamify_ceremony.js`（新規）。既存テストと同じく**実ソースを読み込む**方式で書く。

- キューに2つ積んだとき、1つ目が最後まで再生されてから2つ目が出ること
- `examMode` が真の間は再生されず、解除後（結果画面）にまとめて再生されること
- 溜まったものが失われないこと（順序も保つ）

## 3. Phase 2 — 試験経路の演出【本命】

### B1. 科目読み込みの待ちが完全に無演出【最優先】

`study.html` の `toggleSubjectChip()`：

```js
const need = [...selectedSubjects].filter(s => !_loadedSids.has(s));
if (need.length) Promise.all(need.map(s => _fetchSubjectCards(s))).then(_finish);
else _finish();
```

**最大594問（神経）のJSONを fetch する間、表示が一切ない。**
押した手応えも `_syncChipStyles()` の色替えだけ。

**経路の中で唯一の無演出区間であり、毎回必ず通り、毎回いちばん長く待つ場所。**

- チップ自体が「読み込み中」を持つ（縁の脈・進捗リング）。
  ハブの `.cta-redo[data-load]::before` と同じ作りが流用できる。
- カードは上から波状に着地させる（`--i` スタッガー。ハブのボタン入場 E3 と同じ手法）。
- 完了時に科目色で一度だけ走査（`MecFX.wave`＝既存エミッタ。新規追加は不要）。

⚠️ `_unloadSubjectCards` → `_fetchSubjectCards` → `_finish` の順で、`_finish` の中で
`_buildChapterMap()` 等が `requestAnimationFrame` 越しに走る。**演出の終わりをここに合わせること**
（先に演出が終わると、まだカードが並んでいない画面が見える）。

### B2. 進捗バーの「距離感」【最優先】

`study_exam.js` の `_updateExamProg()` は**バーの幅が伸びて数字が跳ねるだけ**。
50問セッションだと、連続正解が切れている間（＝実力的に一番苦しい時間帯）は演出がゼロになる。

**⚠️ 設計上の決定：節目は「祝わない」。距離感を示すだけにする。**
連続正解（tier）と別軸で祝う演出を足すと tier 演出とぶつかり、画面が騒がしくなるため。

- 進捗バーに**目盛り**を打つ（半分・残り10問）。跨いだ瞬間に光が走るだけ。**音も粒子も出さない。**
- バー上に**難問（`data-rate < 60`）の位置を印として置く** ＝ 残りに何が待っているかが見える。
- 残り5問から盤面の色温度をゆっくり上げる（ラストスパート）。
  これは連続正解と独立した軸なので tier と競合しない。

⚠️ 難問の判定は `data-rate` が正本で、閾値は **`HARD_RATE = 60`**（`gamify.js` と study.html の
フィルタ「難問(<60%)」と同じ数字にすること）。**`data-rate` 属性が無い問題（正答率なし）は
難問に数えない**——出典に数字が載っていないだけで、難しいという意味ではない。

### B3. 結果画面の難問可視化

`showExamSummary()` に「難問 8問中 5問正解」を出す。
B2・B4 と**同じ `data-rate` 1本が経路を貫く**構成にすること（予告 → 道中の印 → 結果）。
「難しいところに挑んだ」という事実が3回別の形で返ってくる。

既存の A1（難問クリアの刻印）と世界観が揃う。

### B4. 開始モーダルの予告

`study.html` の `#examStartOv`。**開始を押すまで何問出るのか分からない**（分母は `startExam()` で確定）。

- 章チップ・フィルターを触るたびに「この条件で **N問**（うち難問 **M問**）」をリアルタイム更新。
  演出であると同時に情報。
- モーダル自体の入場アニメも無いので付ける。

### B5. 結果画面を閉じた後

`closeExamSummary()` は overlay を閉じて科目を読み直すだけ。余韻も次への導線もない。

- 閉じる動作に「幕が下りる」余韻。
- 戻った先で、今解いた問題が**成績付きで並び直す**（誤答が赤く残る）。今は普通のカードに戻るだけ。

### B6. 選択肢のシャッフルを見せる

「選択肢はシャッフルされます」はモーダルの文字でしか伝わっていない。
**1問目のカードだけ、選択肢が一瞬並び替わる動きを見せる。**
「毎回違う配置で来る」が体で分かり、暗記ではなく理解で解く感覚に繋がる。

⚠️ **下線部がある問題（`<u>`）はシャッフルされない**。この演出も出さないこと。

### B7. 1問目のカード入場を特別扱いする（小）

カウントダウン（C9）の直後、1問目の入場が2問目以降と同じ。開幕だけ登場を作る。

### B8. 誤答再試験を「リマッチ」として演出する（小〜中）

`retryWrongExam` は今、普通に始まる。落とした問題を相手に見立てた入り方にする。
既存の C2（RECOVER）と世界観が揃う。

## 4. Phase 3 — stats.html の再構成【減らす → 動かす】

### 4-1. 現状の診断（ユーザー確認済み）

セクションが **14本**あり、うち重複が2組ある。

**「弱いもの」のリストが4本：**
📐本番との差／💡取りこぼし問題／🎯苦手問題ランキング／🔍誤答選択肢パターン。
どれも uid 単位のリストで**同じ問題が複数に重複して載る**。
4本を見比べないと「次に何をやるか」が決まらない。

**「時間の記録」が3本：**
🗓学習カレンダー(12週)／📅30日間の学習記録／⏱30日間の学習時間。ほぼ同じ期間の同じ話。

**そのほか：**

- 🤖 AI相談用データが**ページの上から2番目**にある。道具であって情報ではない。
- `chartSec` / `gapSec` / `missSec` が `display:none` から出入りするので、
  **日によってページの形が変わる**。「あの表はどこだっけ」の原因。
- 🗺 章別ヒートマップが **180章**を一度に出している。
- 母数の扱い（`HM_MIN_N = 3`・薄いセルは「—」）は**既にきちんとしている。ここは触らない**。

### 4-2. 📐「本番との差」は廃止する

`renderGap()` の計算：

```js
const mr  = Object.entries(myrate).filter(([uid]) => isIn(uid));  // 自分が解いた問題だけ
const nat = Object.keys(RATE).filter(isIn).map(u => RATE[u]);     // その科目の全問
diff = (自分が解いた問題の正答率) - (科目の全問の本番正答率の平均)
```

**引き算の左右で分母が違う。**
左は「自分が試験モードで解いた問題」、右は「その科目の全問」。
難問フィルターで解いていればそれだけで差はマイナスに振れ、易問ばかりならプラスに出る。
**数字が何を意味するのか原理的に読めない**（ユーザーの「何を意味しているのか不明」は正確な直感）。

正しくやるなら**同じ問題集合で比べる**（自分が解いた uid の本番正答率の平均 vs 自分の正答率）。
**ただしその形は既に2箇所にある**——
「💡取りこぼし問題（本番正答率80%以上なのに落とした）」が uid 単位で同じことをやっており、
「本番正答率帯ごとの自分の正答率」（`bandRows`）が同じ軸をより丁寧に見せている。
作り直すと3つ目の重複になる。

→ **廃止し、弱点統合リストへ吸収する。**

### 4-3. 新しい構成（4層）

```
1. 今の状態
     済み / 連続🔥 / 今日の学習時間
     国試までの日数とペース（必要ペース vs 直近7日の実績）
     🔔 復習の見通し

2. 積み上げ
     🗓 学習カレンダー(12週) を主にする
     30日の解答数・学習時間は カレンダーのセルの内訳（既存 #calReadout）へ吸収
     ✅ 済みレベル分布 / 📈 科目別正答率の推移 はここ

3. どこが弱いか
     弱点リストを1本に統合（各行にタグ 🔻本番差 / 💡取りこぼし / 🔁反復ミス）
       ← 📐本番との差(廃止) / 💡取りこぼし / 🎯苦手ランキング / 🔍誤答選択肢パターン を合流
       ← 🔍誤答選択肢パターンは各行の詳細（展開）へ
     🩺 弱点カルテ（科目 × 設問形式）
     🗺 章別ヒートマップ → 科目を選んでから章、の2段にする

4. 道具
     🤖 AI相談エクスポート（末尾へ移動）
```

- `display:none` の出入りは、**空の状態を「まだデータがありません」で常設**して解消する
  （ページの形が日替わりで変わらないようにする）。
- **統合リストの各行から study.html へ直接飛べること**を必ず確認する
  （`study.html?sid=X&filter=weak` の経路が既にある）。

### 4-4. 整理が済んでから演出を載せる

**順序を守ること。減らす前に動かすと、読みにくいものが動くだけになる。**

- セクションの入場リビール（上から順・**セッション内で1回だけ**。開くたび全部動くと重い）
- 数字のカウントアップ
- カレンダー／ヒートマップのセルを波状に着色（ハブの30日波形と同じ書き方）
- 国試カウントダウンのリング、ペースバーが動く
- 「今日」のセルだけ呼吸する

⚠️ **`_tweenNum` 系には rAF が止まった時の落とし所を必ず付ける**（`setTimeout(finish, dur+400)`）。
非表示タブでは rAF が動かないので、保険が無いと**裏で開いた stats の数字が0のまま凍る**
（ハブで実際に起きた。index.html の `_tweenNum` が参考実装）。

## 5. Phase 4 — 筐体／盤面の分離による意匠統一【最後】

### 5-1. 衝突している前提

- ハブ（index.html）＝ **真鍮・銅で固定**。テーマに振らない。
- 試験モード（study_exam.js）＝ **7テーマでランダムに配色が変わる**。

**片方に寄せると、もう片方の意味が壊れる。**

### 5-2. 解決：「筐体」と「盤面」を分ける

| 層 | 色 | 中身 |
|---|---|---|
| **筐体**（シャーシ） | **真鍮固定・全ページ共通** | 枠・リベット・ベント・歯車 |
| **盤面**（表示） | **テーマ色で可変** | 進捗の弧・数字・粒子 |

「同じ機械の中にいる」感覚は筐体が担い、「今日はどのテーマか」は盤面が担う。

**これはハブのゲージが既に採っている分け方**（`--brass`/`--brass-hi`/`--copper` の歯車と、
`--or`／達成の `--gr` の弧を別系統の色にしてある）と同じ思想なので、新しい規約を作らずに済む。

### 5-3. Phase 4 を最後に置く理由

B の部品（進捗バーの目盛り・難問印）が出揃ってから枠を被せた方が手戻りが少ない。

### 5-4. 注意

⚠️ 試験ヘッダ（`.st-hdr`）は **iPad で約180px** を占める。情報を削らずに意匠だけ載せること。
可視帯（`_fxBand()`）はヘッダ下端を基準にしているので、**ヘッダの高さを変えたら演出の焦点が動く**。
`node _work/test_fx_band.js` が帯の幾何を検査するので必ず通す。

⚠️ CSS変数を足すときは**接頭辞を必須にする**（例 `--gauge-` / `--cta-` / `--exam-`）。
`--cb` のような短い名前は `vars.css` の共通トークンと衝突し、
**`animation: X var(--cb,3.4s)` が色を duration に食ってプロパティごと `unset` になる**
（2026-08-14に実際に起きた。4つ中1つだけ動くという気づきにくい壊れ方をした）。

## 6. 全フェーズ共通の制約（既存の規約・破ると壊れる）

- **発火位置は `_fxBand()`（study_exam.js）が正本。** `window.innerHeight * 0.4` のような
  画面基準の座標を新しく書かない。
- **`document.body` を transform しない。** transform された要素は `position:fixed` の
  包含ブロックになるため、揺れている間だけ全演出がページ先頭基準になって画面外へ飛ぶ。
  画面を揺らすなら `_shakeFxLayers()`。
- **正解／誤答の追加演出は `_afterCorrectFx` / `_afterWrongFx` へ足す。**
  正解の経路は2つある（`revealAnswer`＝選択肢／`_revealCalcAnswer`＝計算問題の桁入力）ので、
  片方に直接書くと**計算問題50問だけ演出が抜ける**。
- **`fx_engine.js` のエミッタ追加は常に純増で行う。** 既存関数の引数や既定値を変えると7テーマ全部に波及する。
  位置を自前で持つ型は **`STATIC_TYPES` に登録必須**（忘れると重力で1フレームで消える）。
- **1要素で使える層は3つだけ**（本体の `animation` / `::before` / `::after`）。
  同じ層に2つ置くと後勝ちで片方が黙って死ぬ。
- **tier で配列・マップを引くときは `_tIdx(tier, o)` を使う**（`Math.min(tier, 6)` を新しく書かない）。
- **reduced-motion（`_mecReducedMotion()` / `_fxOk()`）を必ず通す。** 常時ループは
  非表示タブ・画面外でも止める。
- **`prefers-reduced-motion` 時に「消えるだけ」にしない。** 動きの代わりに静的な印（色・字・枠）で
  同じ事実を出す（ハブは既に二重化してある）。優先度は低いが設計としては守る。
