### ⚠️ 不変条件（破ると「重い・使いづらい」が再発する）

旧実装が重かった主因は**ノード数ではなく描画方式**だった（72ノード・約800要素はSVGとして軽量）。

1. **`infinite` アニメーションを1つも置かない。** 試験モードの Phase 4/5 は「読んでいる8〜15秒を
   埋める」ためのもので**目的が違う**。ここは眺めて思い出す道具で、動くものは視線を奪う。
   動くのはタップした瞬間の `.mm-pulse`（0.62秒・JSが要素ごと消す）だけ。
   旧実装は `flow`/`travelDot`/`orbitSpin`/`twinkle`/`pulse` が常時回っていた。
2. **SVGフィルタ（`filter:url(#…)`）を使わない。** glow は半透明の同心円を重ねて焼く。
   旧実装は `feGaussianBlur stdDeviation:55` を10枚重ね、拡縮のたびに再ブラーしていた。
3. **巨大SVGを CSS `transform:scale` で拡縮しない。拡縮は `viewBox` の書き換えで行う。**
   旧実装は 2000×2000 の SVG を scale 3 まで拡大でき、ドラッグ中は `will-change:transform` で
   レイヤー昇格して **6000×6000×4B ≒ 144MB のテクスチャ**になっていた（iPadが最初に落ちる場所）。
4. **章の色・角度をデータに持たない。** 色は `MM_PALETTE[章index % 11]`、角度は章数から自動計算。
   ⚠️ 旧データの章 `color` は「系統色」ではなく**隣接章を見分けるための回転パレット**だった
   （「内分泌の基本」が橙＝代謝系、「脂質代謝」が赤＝炎症系、「甲状腺」が緑＝自己免疫系）。
   `_work/mindmap_generation_prompt.md` の「系統でグループ化」は一度も守られていない。
   系統で塗り分けたくなったら、**意味のある軸を別に設計してから**入れること。
5. **走るアニメーションは常に1本**（`animToken` で世代を持つ）。旧 `panTo` は呼ばれるたびに
   新しい rAF ループを立てており、科目を連続タップすると**レンダラが応答しなくなった**
   （スクリーンショットが30秒タイムアウトした＝実測）。
6. **進捗オーバーレイ（済み率・正答率でノードを塗る）を入れない。** 章色という意味の色が既に
   載っている面に別軸の色を重ねると両方読めなくなる（Phase 4 の「筐体は真鍮固定／盤面は意味色」
   と同じ論理＝1つの面に2つの意味を持たせない）。弱点の可視化は stats.html の担当。
7. **疾患ノードの位置は `<g transform="translate(x,y)">` の提示属性が正本＝CSS で `transform` を
   動かさない。** CSS の transform は提示属性を丸ごと上書きするので、入場アニメで
   `transform: scale()` を当てた瞬間に**全ノードが原点（盤面の中央）へ折り重なり、病名が白文字の
   山になる**（2026-08-22に演出強化で実際に起きて、全科目のマップが使えなくなった）。
   動かすなら独立プロパティの `scale` / `translate` / `rotate`（translate と合成される）。
   ⚠️ **入場アニメで `opacity: 0` を使わないこと**——ベース規則でもキーフレームの 0% でも。
   非表示タブでは CSS アニメーションが1frameも進まず先頭で凍るので、ノードが見えないまま残る
   （stats.html の `armReveal` と同じ穴）。`scale` だけなら凍っても 0.6 倍で見えて押せる。
   `test_mindmap_layout.js` の §10 がこの2つを検査する。
8. **習熟度・正答率でノードを塗らない**（6 と同じ理由）。2026-08-22に `myrate_v1` を引いて
   ノードの縁を塗る実装が入ったが、**引いていたのは疾患ノードのid（`d01a`）で uid ではない**ため
   一度も一致せず、全ノードに同じ縁が付くだけだった。撤去済み。
9. **`fit()` は背景（`lBg`）と演出（`lFx`）を測らない。** 背景の目盛り円は疾患リングの大きさで
   描かれるので、何も展開していないハブだと「中身は中心の10ノードだけなのに外形は疾患リングぶん」
   になり、地図が画面中央で豆粒になる（実機で確認）。外形は `getBBox()` の実測で取る
   （レイアウトの計算値から見積もると縦に27%の余白が出た）。

### レイアウトは1つの関数で全部を賄う

`computeLayout(parents, isOpen)` が科目マップ（親＝章）とハブ（親＝科目）の両方を計算する。

```
R1   = max(250, N*(2*CH_R+CH_GAP)/2π)     親リング半径（Nから決まるので親は絶対に重ならない）
扇   = min(子が1リングに収まる幅, 隣に迷惑をかけない上限)
      閉じている隣の区画は丸ごと借りられる（閉じた親に子は無いので衝突しない）
入りきらない子は R2 + k*RING_STEP の外側リングへ積む
```

- ⚠️ **扇の `min(必要なぶん, 上限)` の `min` を外さないこと。** 外すと余裕のある科目マップでも
  扇が開閉のたびに伸び縮みして**ノードの位置が動く**＝「どこにあったか」の記憶が壊れる。
  テスト §5 が「1章を閉じても他章の疾患が1pxも動かない」を見張る。
- これで**感染症22章もハブ21科目も同じ関数で載る**。旧実装は1周を科目数で割るだけだったので、
  21科目にすると 17.1°間隔・fan 14°・弧173px となり、直径54pxの疾患ノードは3個で埋まって破綻した。
- ⚠️ **ハブに「すべて開く」を置かない。** 21科目×代表8疾患を同時に置くと、どの科目も隣の角度を
  借りられず必ず衝突する（幾何の要請であって好みではない）。同時展開は `HUB_MAX_OPEN = 3`。

### ハブは科目マップの射影ではない

`_hub.js` の72疾患（科目あたり8つ）は**独立に選抜された見取り図**で、科目マップの320疾患と
ラベルが対応するのは72件中55件、`keys` の粒度も違う（科目全体を俯瞰する高さで書かれている）。
段Cで新科目を足すときは、**科目データとハブの代表疾患8つを別々に書く**。これは重複ではなく
「その科目を定義する8つを選ぶ」という別の作業。

### 新しい科目のマップを足す手順（段C）

1. `mindmap_data/{sid}.js` を書く（章 → 疾患5〜8個 → `keys` 4行、`relations` は5〜12本）
2. `_hub.js` の `subjects` に代表疾患8つを足す
3. `node _work/build_mindmap_index.js`（`ready:true` になる）
4. `sw.js` の SHELL に `./mindmap_data/{sid}.js` を足す
5. `node _work/test_mindmap_layout.js` を通す

⚠️ **`keys` に書いてよいのは数値・略語・鑑別の分岐を含む具体的な記述だけ。**
「重要」「頻出」のような形容は1行使って何も伝えないので禁止。既存の水準を基準にする
（`小球性低色素性（MCV↓, MCHC↓）` `t(15;17) → PML-RARα融合遺伝子`）。

⚠️ **`{科目}/mindmap.html` を新しく作らないこと。** そこにあるのはリダイレクトのstubで、
エンジンを科目ごとに持つ形へ戻すと study_exam.js ⇔ chapter_exam.js と同じ乖離を21方向で踏む。

⚠️ **章の構成は questions_*.json をそのまま写さない科目が2つある。**
`kansen` は「第N章」の見出し行が0問で、問題は §N の節に入っているので**問題のある15節を章にした**。

（内容は各章のノードに含まれる）。ここを機械的に揃えようとしないこと。
